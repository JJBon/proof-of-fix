# Design

## Context
- **Why:** see proposal.md. The behaviour is in `specs/deployment-binding`, `specs/canonical-head`, `specs/radicle-hosting`, `specs/public-release`, `specs/panel-liveness` and the deltas to `validator-admission`, `judge-panels`, `reputation` and `bounty-market`. This document covers how, the parameters, the Radicle spike and the order of work. Decisions here are numbered **L1–L25** so they don't collide with #132's D-numbers, which are referenced as they are.
- **v3 today** (`contracts/src/v3`, [`reports/devnet-v3-local.md`](../../../reports/devnet-v3-local.md)): Validators, Panels, PanelScores, FeesV3, PoolV3 and RaceV3 run beside v2 on a local devnet, with the `simulated` proof type and the fake judge. #132's rules decided after the judge measurement (D20 seats by rank, D21 the test dispute, D24–D30) were in its specs and the simulation, not in the contracts (`docs/paper/open-problems.md` 7.5), until contract batch 3 (2026-11-19) built D20, D21, D24, D27, D29, D30 and L6 (tasks 3.3 and 3.6).
- **Radicle today:** #190's spike ([`reports/radicle-spike-v1.md`](../../../reports/radicle-spike-v1.md)) showed a threshold merge gated by `Heads.head`, with three fixed judges as delegates. #201's adapter (`oracle/radicle.py`) and `pofctl verify-head` work for v2's fixed seats. The spike's limit: **v3's per-draw judges can't be Radicle delegates**, because the delegate set changes only by a threshold of the current delegates, and a new delegate must have published `main` first.

## Goals / Non-Goals
**Goals:**
- A v3 deployment that can only serve proof-of-fix and can only be constructed on Sepolia, with its windows chosen per deployment.
- A head on-chain that never names a fix whose verdict was reversed.
- A Radicle merge model for changing panels, chosen by a spike, with a check anyone can run.
- Every public step behind the owner's go, recorded.

**Non-goals:**
- Preventing forks from deploying the code without these checks. It can't be done in open code, and the specs say so.
- Changing any #132 decision. D20, D21, D24, D27, D29 and D30 are built as #132 records them. Their values were decided on 2026-11-19 (#132 tasks 10.2, 11.2 and 12.2, [ADR 0007](../../../docs/adr/0007-solver-side-parameters.md)); this change only records that decision in #132's tasks and design.
- Validator capacity and per-repository rate limits (#253) and validators' repository choice (#252).

## Decisions

### L1. One repository, an immutable constructor argument
- **The rule:** `RaceV3`'s constructor takes `repo` (`keccak256(RID)`) and `genesisHead` instead of arrays. `Heads` is created with that one entry. `register` refuses any other id and zero (`deployment-binding`).
- **Why both refusals:** a zero repository would let a bounty be won without the head moving, which is a way around the merge rule.
- **`FeesV3`'s per-repository profiles:** one profile, for this repository; the default profile is unused.
- **Alternative rejected:** a list fixed at deployment with one entry. It keeps the code path for many repositories in the deployed bytecode and invites a second entry in a later deployment record.
- **The limit, stated:** this binds the deployment. A fork removes it with a one-line change; the README and the paper say so.

### L2. Sepolia only, at construction and in the deploy script
- **The rule:** each v3 contract's constructor reverts unless `block.chainid == 11155111`. The deploy script reads `eth_chainId` before signing anything and stops unless it is 11155111.
- **The conflict with local testing (decided by the owner on 2026-11-18: option 1):** the devnet (7193), anvil (31337) and Foundry tests need to construct the same contracts, and the `simulated` proof type is accepted only on 31337 and 7193. Three ways:
  1. **(recommended)** the constructor accepts 11155111 and the two local test ids already named in `Validators.sol`. On any other chain, mainnet included, it reverts. On Sepolia the `simulated` type is refused, as today.
  2. Exactly 11155111: local runs use `anvil --chain-id 11155111` and `vm.chainId`, and the simulated attestation needs another switch, which then exists in the Sepolia bytecode.
  3. A build profile with a different constant per chain: two bytecodes, so the audited one isn't the tested one.

  **Decided: option 1.** It matches the owner's intent (no deployment on a chain with value) and keeps one bytecode. Its risk: a public chain that reuses 31337 or 7193 could host a deployment, with the `simulated` type accepted. The deploy script refuses both ids for anything but a local endpoint.
- **Why also the script:** the constructor check costs a deployment's gas to discover; the script stops before signing.

### L3. A keyless deploy from a fresh wallet
- A new externally owned account, funded from a Sepolia faucet, deploys and has no role afterwards: no owner, admin, upgrade or pause (ADR 0002, D15). The deployment record names it.
- **The deploy script** (`contracts/script/DeploySepolia.s.sol` and a shell wrapper) is a dry run by default, and broadcasts only with an explicit flag naming the step (`public-release`). Before anything, it checks:
  - the chain id (L2);
  - that the Radicle repository exists and its canonical `main` is the genesis head given (`pofctl verify-head --rid … --commit …`);
  - that the windows pass the constructor's order check, by simulating the deployment locally first.
- **Order:** the Radicle repository first (task group 6), then the deploy (group 7). The genesis head is the Radicle repository's root commit, or its `main` at the moment of deploying.

### L4. Windows as constructor parameters
- **The rule:** a `Windows` struct passed to `Panels` (and the derived unbonding delay to `Validators`), stored as immutables, readable, and listed in the deployment record. The constructor checks order (`deployment-binding`).
- **Contents:** `SEAL_WINDOW`, `REVEAL_WINDOW`, `CHALLENGE_WINDOW[k, level]` for k ∈ {1, 3, 5, 7} and levels A and B (level C's entries are kept in the struct but unused on a TEE-only deployment), `ADR_WINDOW`, `REMOVAL_WINDOW`, `K1_WINDOW_MIN`.
- **Derived:** `UNBONDING_DELAY` = the longest challenge window + `UNBONDING_MARGIN` (7 days), as #132 already defines it (504 h with today's values).
- **Why constructor parameters and not a setter:** a setter is a key (D15). Different deployments (devnet in minutes, Sepolia, a fork) need different values; one deployment never changes.
- **Values for Sepolia (decided by the owner on 2026-11-18: the production values):**

  | Name | Production values (ADR 0004; ADR 0007 keeps them until they are re-derived) | Shortened alternative | Why |
  |---|---|---|---|
  | `SEAL_WINDOW`, `REVEAL_WINDOW` | 2 h, 1 h | 2 h, 1 h | judges on real hosts need the time either way |
  | `CHALLENGE_WINDOW[1, A]` | 168 h (level B: 336 h) | 24 h (B: 48 h) | a lone verdict needs time for anyone to re-run it |
  | `CHALLENGE_WINDOW[3, A]` | 24 h (B: 48 h) | 6 h (B: 12 h) | |
  | `CHALLENGE_WINDOW[5, A]`, `[7, A]` | 12 h, 6 h (B: twice) | 3 h, 2 h | |
  | `ADR_WINDOW`, `REMOVAL_WINDOW` | 14 days, 48 h | 14 days, 48 h | an ADR's notice isn't a speed question |

  **Decided: the production values.** The owner's thesis is to measure the time to heal (#248); a testnet with shortened windows measures a different system. The shortened column stays documented as the alternative, not used on Sepolia.
- **How it's tested:** the Foundry suite runs with production values and with minutes; the devnet run (#248's `scripts/time-to-heal.sh`) runs with minutes, so a reversal is measured in wall-clock time on a real clock, which task 5.2 of #132 needed.

### L5. A bond below the floor is a visible state
- **The rule:** the registry treats "active with a bond below `BOND_FLOOR`" as its own state, `BelowFloor`, entered and left inside `_rebucket` (or wherever the bond changes), with an event each way; `activeCount` excludes it (`validator-admission` delta).
- **`topUp`** to the floor returns it to `Active` without qualifying again: it was qualified, and only its bond changed. **`leave`** works from `BelowFloor` with the same unbonding conditions.
- **What counts it:** everything that reads `activeCount` (the shadow rate while fewer than `K_MAX` are active, the k = 1 hold, FeesV3's idle signal) no longer counts a validator that can't be drawn. That is the bug in finding 7: a challenge waited for a validator that looked active.
- **Alternatives rejected:**
  - **Slash into a separate margin above the floor:** the floor then moves up by the margin; a second slash brings back the same state.
  - **The node tops up on its own by default:** it spends the operator's coin without asking. It stays an option the operator configures.
- **How it's tested:** a Foundry test per scenario of the delta, an invariant (`activeCount` equals the count of `Active` validators with bond ≥ floor), and the devnet run without the script's manual top-up.

### L6. "Active solver" and the minimum of three
- **The rule** (`bounty-market` delta): an identity is active while, within `ACTIVE_WINDOW`, it has a final passing fix or an upheld failing-test dispute in the repository. Pledges are refused while fewer than `ACTIVE_SOLVERS_MIN` are active. Issues can still be registered and fixed with no funds.
- **Decided (owner, 2026-11-19, #251; [ADR 0007](../../../docs/adr/0007-solver-side-parameters.md)):** `ACTIVE_SOLVERS_MIN` 3 and `ACTIVE_WINDOW` **26 weeks**, counting **only the repository's own solvers**: an upheld dispute counts only for an identity that has a final passing fix in the repository ([`reports/active-solvers-v1.md`](../../../reports/active-solvers-v1.md), task 3.2). No solver's deposit, and no deposit while the count is low. The sybil of three stays a named trust point (below).
- **Why three:** report v5 (section 2 and the post hoc rows): R+F holds, every attacker at or below its twin, with 3 and 10 active honest solvers finding a failing test 1 time in 4 (assumed); with 1 it leaves gains of $237–3,870 a year per attacker. The owner chose the minimum instead of a deposit (2026-11-17, #251; no deposit, #250).
- **Why these two events:** they are what the chain can see. The simulation's "active honest solver" is one that searches every pass; the chain can't see a search, only its results: a fix that stood, or a test that reversed one.
- **Why unfunded fixes count:** otherwise no repository could ever reach three, since nothing can be pledged before.
- **`ACTIVE_WINDOW`: 26 weeks, decided 2026-11-19** (13 weeks was proposed first: long enough that a solver working a few issues a quarter stays counted, short enough that a repository whose solvers left stops taking new money within a quarter). Task 3.2's pre-registered rule picked 26: 13 weeks leaves +2.4 ± 0.8 and +3.4 ± 0.9 more good fixes unpaid a year in a repository of 1 issue a week with 3 solvers, and no attacker row differs between windows. The cost: a repository whose solvers all left keeps taking pledges for up to half a year.
- **Why only the repository's own solvers count:** if anyone's upheld test counted, as this section first said, contenders would open a one-solver repository within about 2 weeks, and every attacker of report v5 would gain again (up to +$3,399; active-solvers-v1, section 2.3). The narrower count is not simulated.
- **The named trust point:** one party can make three identities active with three good fixes (three judges' fees and three fixes' work). Then the minimum is met by one solver, which is report v5's failing case. What bounds it: D29's cap (each new identity starts at $50 of open claims), and every bad fix still faces the panel and disputes. Measured by task 3.2's simulation, not assumed.
  - **Measured (active-solvers-v1):** with one honest solver the sybil gains up to +$3,680 ± 384 a year, for about $106 and 19 fixes a year at 13 weeks, or $64 at 26 weeks (23 faucet requests at a $40 fee). With 3 and 10 honest solvers it gains nothing. A higher minimum, a longer window or dearer fixes don't close it; only a deposit of about 25 % does, and the owner declined one (2026-11-19). **It stays a named trust point, reported in the README and the paper.**
  - **The gate's one other gap:** the long con under GPT-6.1 with 3 solvers is +$451 ± 336 a year above its twin. It is at even without the gate too, so it is R+F's margin, not the gate's.
- **Funded bounties continue when the count falls:** refusing them would strand funders' coin; the count only gates new money.
- **How the simulation tests it** (task 3.2): `pof/sim/openval/nodeposit.py` gains the pledge gate and the on-chain definition of active, with report v5's attackers plus a **sybil of three** (one party's three identities unlocking pledges, then submitting bad fixes), on 1, 3 and 10 honest solvers; rows by `ACTIVE_WINDOW` (6, 13, 26 weeks).

### L7. D29 and D30 in the contracts
- **As #132 records them** (`reputation` and `bounty-market` deltas), **decided 2026-11-19** ([ADR 0007](../../../docs/adr/0007-solver-side-parameters.md)): `REP_BASE` $50, `REP_MULT` 1, `REP_LOSS_X` 2 (`REP_ON_REVERSAL` "minus": a reversal subtracts 2 × its bounty, it doesn't reset). `JUDGE_FEE` is one flat fee per submission in place of per-check charges, re-measured each period from the validators' posted costs (report v5: $5.03 on its base network). **On Sepolia D30 is the pure taxi fare (owner, 2026-11-19): `judgeFee` 0**, a fix posts FeesV3's worst-case deposit, its judges are paid by the meter and the rest returns to the solver; the flat fee (first $40, L17) is deferred to a mainnet decision. On Sepolia the amounts are in the test coin.
- **No solver's deposit** (owner, 2026-11-19): `SOLVER_DEPOSIT_BPS` is 0 and absent. A rejected fix costs its solver its panel's metered checks only (the taxi fare on Sepolia).
- **The identity is the solver's address.** Report v5's free-identities attacker (S) already plays one address per fix; the cap held from 3 solvers.
- **Where they are built:** #132 task 12.5 (contracts) and 12.6 (node, pofctl). **Built 2026-11-19** (contract batch 3, with 10.4 and 11.4's accepted parts): the race's `SolverBook` (reputation, claims, active solvers) and `Config.judgeFee`, a constructor argument (0, the taxi fare, in the Sepolia deploy script since the owner's change of 2026-11-19; a flat fee above 0 stays in the code for a mainnet decision). This change doesn't duplicate them: its task 3.6 checks they are in the deployed set and adds the launch's tests. If #132's tasks haven't run when the launch needs them, they are done there, under #132's ticket.
- **D21 and D20 are needed too.** R+F's result rests on rivals' failing-test disputes (D21), and a network whose validators run one family stalls under the family cap without D20 (open problems 7.5). Both are #132 task 10.4, a dependency of the deploy.
  - **Their values, decided 2026-11-19:** D20's `SEAT_MARGIN` 5 points and `CAP_MIN_FAMILIES` 3; D21's `EVIDENCE_STAKE` the larger of $5 and 10 % of the bounty, and `EVIDENCE_REWARD_BPS` 1,000 (report measured-v3).
  - **With no deposit, the reward is a disputer's only pay besides its stake back.** At 1,000 a rival's search of a passed fix doesn't pay with per-issue bounties (report v4, section 7), so R+F rests on honest solvers who search anyway, each finding a failing test 1 time in 4 (assumed in report v5).
  - **D21's two rates are assumed, not measured** (#132 task 10.3, a paid run the owner hasn't decided). At the launch, D21's safety rests on them: a named trust point.

### L8. D27 and D24 are in the launch set
- **Decided for the launch (owner, 2026-11-17, #251):** while fewer than `CAP_MIN_FAMILIES` families can judge, a challenge that can't draw D4's larger fresh panel is judged by a second draw of the original size from those families. Its spec text is #132's `judge-panels` requirement "A challenge among few families gets a second draw"; its `(proposed)` mark went on 2026-11-19, when #132's task 11.2 recorded the decision.
- **`SECOND_PANEL` ("few families" or "always")** was #132's open question; the launch takes whatever 11.2 records. **Decided 2026-11-19: "few families"**, only while fewer than `CAP_MIN_FAMILIES` (3) families can judge. Without D27, report v4 found 23 % of verdicts never final under one family, which on a testnet of a few validators is most of them.
- **D24, the appeal on evidence, is in the launch set too (owner, 2026-11-19):** a rejected fix's one appeal needs a test that fails on the base code and passes with the fix, and, **since 2026-11-19 (owner), no stake**: an appeal pays only its fresh panel's metered validation, as a submission does (the stake, the larger of $5 and 10 % lost to the sponsors' pool, is dropped); the seated families decide; `APPEAL_WINDOW` 72 h (report v3's value; no result depends on it). Its spec text is #132's `judge-panels` ("An appeal needs a test", "What an appeal costs"). Accepted risk: a solver may appeal every rejection, paying each panel's meter, the same spam risk as submissions (L17). Its two rates are assumed (#132 task 11.3, not decided): a named trust point at the launch.
- **Not in the launch set:** D25 (sponsorship) and D26 (known answers), deferred by the owner on 2026-11-19. D26 waits for #136; D25 can follow after the launch.
- **Built by** #132 task 11.4's accepted parts: the appeal and the second draw (`Panels`), and the stake's two destinations (`RaceV3`).

### L9. The head moves at finality
- **The rule** (`canonical-head`): `claim` no longer calls `Heads.move`. A new call, `merge(bounty)`, which anyone may make, moves the head once the winning verdict is final; until then the bounty is `Won`/claimed but not merged. Instalments still start at finality, as today.
- **Why:** today a fix reversed inside its window stays as the head, and the next fixes are based on it. Radicle's `main` (any of the candidates in L11) would then carry a reversed fix, and the only way out is a new fix that reverts it, judged and paid.
- **The cost:** the next fix to the same code waits for the previous one's finality: 24 h for a level A panel of 3 with production windows, 168 h plus any hold for k = 1. Fixes to different files still rebase cleanly. `scripts/time-to-heal.sh` measures it.
- **Alternatives rejected:**
  - **Move at claim and add `Heads.revert`:** the head can go back to the base only if nothing moved since; otherwise the chain can't compute the reverting commit. A frozen head then blocks every bounty.
  - **Keep it as it is:** a reversed fix in `main` with no automatic way out.
- **The stale-base rule** stays v2's (S1): at `merge`, the base must be the head, or the call reverts and the winner keeps its place until the merge deadline.

### L10. TEE only
- A constructor flag, `teeOnly`, true for Sepolia: `Validators` refuses the zkTLS proof type at genesis and in `applyAdr`. The `simulated` type is already refused off local chains (D18).
- **Why a flag and not leaving zkTLS off the genesis list:** an ADR could add it later (D11). The owner's decision is for this deployment, so the deployment can't change it.
- **Validators' hardware:** level A (a cloud's confidential VM with its attestation) and level B (SEV-SNP or TDX elsewhere). #253 builds the first kit (AWS SEV-SNP).

### L11. Radicle under v3: a spike between three models
The question: who signs Radicle's canonical `main` when the judges change with each draw. Each candidate keeps `Heads.head` as the truth (L9) and differs in what Radicle's own `main` means.

| | (a) Delegates are the seated validators | (b) The chain is the only truth | (c) One merge key in approved enclaves |
|---|---|---|---|
| Identity document | delegates = the validators seated on-chain; threshold = a majority of them | one or a few delegates of convenience; their `main` isn't authoritative | one delegate: a key generated inside an enclave and shared only with attested enclaves (#94) |
| Who moves `main` | every seated node pushes `Heads.head` when it moves (#190's gate: refuse anything else) | anyone may push anything; readers ignore `main` and fetch the commit `Heads.head` names | the enclave pushes only `Heads.head` |
| When seats change | each seated node signs the identity revision whose delegates equal the seats, and refuses others; a new seat first publishes `main` at the head | nothing to do | nothing; a key rotation needs an ADR and a revision signed by the old key |
| Check anyone runs | `verify-delegates` (identity vs seats) and `verify-head` | `verify-head` (the only check) | `verify-head`; the enclave's attestation |
| Fails how | a majority of seated validators colluding moves `main` or the delegates; slow or stuck when many nodes are offline | plain `rad clone`, `git clone` and the explorer show a `main` that may be wrong | a broken enclave (level B physical attack) leaks the key; complex key sharing |

- **Recommended: (a), with (b)'s check as the one anyone runs.** (a) keeps Radicle's own tools showing the judged code, its failure needs a colluding majority of bonded validators, and `verify-head` catches it anyway. (c) depends on #94's key sharing, which isn't built.
- **The genesis delegate:** the owner's node creates the repository (`rad init`), so it is the only delegate until validators are seated. Under (a), its first identity revision hands the delegate set to the seats on-chain and removes itself; until then it is a central point, named in the deployment record.
- **What the spike measures** (task group 2), all on an internal network as #190 (Radicle's `test` network, no route out, anvil, the real v3 contracts with short windows):
  1. (a): identity revisions per seat change, the time for all nodes to converge, what happens when a seated node is offline or below the floor (L5), the largest delegate set Radicle 1.10.x accepts, and #190's negative scenarios (outsider, lone delegate, two rogue delegates) under changing seats;
  2. (b): `pofctl checkout` and `verify-head` fetching the head's commit from any namespace, and what the explorer and a fresh `rad clone` show;
  3. (c): a desk study only, unless #94's enclave key provider exists by then;
  4. for each, a validator fetching a patch's commit and judging it (L12).
- **The spike decides.** Its report names the choice and the reasons; the owner accepts it; then the adapter (task 4.1) is built for that choice.
- **Decided (owner, 2026-11-18): (a), with (b)'s checks** as what tools rely on (`reports/radicle-spike-v2.md`, #261: 22 scenarios, 3 runs in a row). Conditions from the spike:
  1. **Each validator's Radicle node ID goes on-chain at registration**, so a seat maps to exactly one node key, and `verify-delegates` reads it from the chain. Today v3 has no such link; the spike carried signed bindings in the identity document instead. **Decided and built (owner, 2026-11-20):** a signed field of the v3 registration, `Registration.radNode` (the node's 32-byte Ed25519 key), stored in the validator's record and readable by anyone (`Validators.radNodeOf`, the `Registered` event's third topic). The owner rejected a separate setter and keeping the key off-chain. 0 registers no node: the validator still judges, but its seat is never counted as a delegate. A key another registration still holds (not leaving or exited) is refused (`NodeTaken`). A validator changes its node by registering again (a new key, after leaving). The signed document bindings remain only for a registry from before the field.
  2. **`BelowFloor` (L5) is built**, so seats are the drawable validators.
  3. **The gate and the revision review run in the node's adapter (task 4.1)**, with **one pending identity revision at a time**: Radicle 1.10.3 blocks a delegate's second proposal while an earlier one is pending.
  4. **`rad sync` takes the RID as a positional argument** in Radicle 1.10.3. The `--rid` form fails, and every caller hid the error. It is fixed in #190's `gate.sh` and still to fix in `oracle/radicle.py`, the v1 spike script and `tests/integration/radicle.py` (task 4.1).
- **Measured:** each seat change is one identity revision; every node converges in 0.36–0.50 s; Radicle accepts up to 255 delegates; with 2 of 4 delegates offline, `main` lags and `verify-head` flags it until one returns. A rogue majority can move `main` and the delegates, and the checks catch it.

### L12. Bounties on Radicle
- **The issue:** an on-chain issue carries a Radicle issue id (the issue's collaborative-object id, 20 bytes) in its registration. The registration check reads the Radicle issue the way v2's bot reads a labelled forge issue: its text claims the registration (`bot/logic`'s claim format).
  - **Amended 2026-11-20 (owner, #251): the claim is signed by the reporter, and the issue id is not stored on-chain** (`RaceV3.register` takes no issue id; no contract change). `pofctl --v3 issue register --rad-issue <id>` comments three lines on the Radicle issue: `Registration: N`, `Reporter wallet: 0x…` and `Claim signature: 0x…`, the reporter's signature, by the key that registered on-chain (the keystore and devnet-key rules apply), as EIP-191 `personal_sign` over keccak256(abi.encode("pof-registration-claim-v1", chainId, race, registration id, keccak256(RID), the issue's 20-byte id)). A validator accepts a claim only when the signature recovers to that registration's on-chain reporter for its own chain, race, repository and that issue; a claim copied onto another issue, or with no valid signature, is ignored, and with none left it seals a fail saying there is no signed claim. The lowest issue id is only a tie-break between several validly signed claims (a reporter who signed for two issues).
- **The fix:** a Radicle patch on proof-of-fix. The solver's commitment opens to the patch revision's head commit, its base and its salt; the claim (submission id, salt) is in the patch description, as it is in a pull request body today. The node replaces `_find_pull` with a Radicle source that lists patches on its own node.
- **Funding:** `pofctl` gains v3 and Radicle commands (`issue register --rad-issue …`, `pledge`, `submit --patch …`) and a public-chain key path (a keystore file, never printed). A bot adapter (#210) is optional.
- **The model judge's registration check:** the v3 node refuses it with a model judge today and stays silent, paying the silence slash. The launch needs it (task 4.3), since every Sepolia validator has a model.

### L19. A panel that can't complete is released, never stuck (owner, 2026-11-18, from report v6)
- **The gap:** when a counted panel's judge stays silent and no eligible validator is left to replace it, the round never completes, and nothing releases it. In report v6's silence runs, 3–28% of a small target's fixes ended the year stuck, neither paid nor refunded. A launch network of 7–15 validators can reach this without any attacker, from ordinary outages.
- **The rule:**
  1. **Time-out:** a round whose replacements are exhausted ends at its reveal deadline plus `STUCK_GRACE`. The silent seats are slashed as today.
  2. **Back to waiting:** the submission returns to the waiting state, keeping its place, and is drawn again with a fresh seed when the eligible set grows or after `RETRY_DELAY`, whichever comes first.
  3. **Then refund:** after `MAX_REDRAWS` failed rounds, or at the bounty's deadline, the bounty is refunded to its funders. The solver's claim is released with no reputation loss and no slash, because the solver did nothing wrong.
- **Audits too (found by the Radicle spike, #261):** when an audit falls due and no eligible validator outside the panel is left, the verdict never becomes final, and the keeper's `drawAudits` keeps retrying. The same rule applies: after `STUCK_GRACE` the audit is released, the verdict waits for an audit to be drawable, and the bounty is refunded after `MAX_REDRAWS` or at its deadline.
- **Decided (owner, 2026-11-20): an audit nobody can take keeps refunding.** `reports/devnet-v3-local.md` finding 9 (#281) measured it: when a panel seats every eligible validator, the norm on a small network, a random audit that falls due can never be drawn, and after `MAX_REDRAWS` the passed fix is refunded. On the devnet 3.2 % of all verdicts ended this way; with 7 identically bonded launch validators every panel is 7 of 7, so about one passed fix in ten (`AUDIT_RATE_BPS` 1,000) would be refunded after about 72 h. The owner kept the refund rather than waiving the audit, shrinking panels or widening who may audit; it is a named launch limit (Risks). It shrinks as validators are added beyond the largest panel.
- **Invariant (restated 2026-11-20 by L25 to include challenges):** every submission is, at every moment, in exactly one of these states: drawn with a live deadline; waiting with a scheduled redraw; counted with its window running, or frozen by one challenge that is itself drawn with a live deadline or waiting with a scheduled redraw, and that ends by `CHALLENGE_DEADLINE` or at its panel's release (L25); final (paid or rejected); or refunded. No other state is reachable. Before L25 an open challenge had none of these (`reports/challenge-drawability-v1.md`, section 4).
- **Values** (proposed, to confirm by #256's scenario d and the simulation): `STUCK_GRACE` 24 h, `RETRY_DELAY` 24 h, `MAX_REDRAWS` 3.
- **Note (2026-11-20, after L24):** the owner's decision of 2026-11-20 to keep the refund when no validator outside the panel can take a random audit (devnet report finding 9, PR #281) is **practically moot at the launch**. With panels of 3 (L24), 7 validators leave 4 outside every panel, so an audit that falls due finds an auditor unless 4 validators are full, paused or gone at once. The rule stays as written: it still applies to any network where a panel seats every eligible validator.

### L20. A fix can't change the tests that judge it: protected paths (tracked by the owner on 2026-11-19; the choice proposed)
- **The gap:** the command comes from the base (`oracle/checkconfig.py`), but the tests run on `src_root/<head_sha>`, the fix's own tree (`node_v2._check`, `node_v3._fix`). A fix can weaken a test under `tests/` (drop an assertion, skip a case) and pass. Only the judge, reading the diff, might notice.
- **The rule:** `.pof/check.json`, read at the base as today, gains an optional key `protected`: a list of paths, each a file or a directory, relative, with no `..` (at most 32). Before running, the node builds a fresh run tree for the check: the fix's tree with each protected path replaced by the base's copy, from the node's own fetch of the base. A file the fix added under a protected path is removed; a file it changed or deleted comes back as it is at the base. The shared checkout under `src_root` is never changed.
- **Overlay, not refuse.** Both close the gap. Overlay is chosen because:
  - the run doesn't depend on reading the diff right (renames, mode changes, symlinks): the protected paths hold the base's bytes, whatever the fix did;
  - new tests stay possible outside the protected paths, which is where the acceptance test goes today (the fix adds it at the root; the runbook's "The issue");
  - a good fix with a stray edit to a protected test isn't thrown out; that edit just isn't run.
  - What refusing would have given: a simpler rule to state ("a fix may not touch `tests/`"). Its cost: a fix that must also change a test can't be submitted at all.
- **Two safety details:** a protected path whose parent is a symlink in the fix's tree fails the check, so the overlay never writes outside the run tree. A protected path the base doesn't have is removed from the run tree.
- **The acceptance test still runs:** the command is `checkconfig.command`'s, unchanged (the repository's commands, then `python -m unittest -q` at the root), on the run tree.
- **What the receipt and the judge see:** the receipt's `tests` records the protected list and the git tree hash of the run tree. The judge's test-run line, in the node's own words (numbers only), says how many of the fix's changed files were under protected paths and not run. The diff is quoted as today.
- **How a legitimate test change gets in:** a **tests-only fix**, one whose diff touches only protected paths (its issue says a test is missing or wrong). The node runs it with both sets: the base's protected tests, as for every fix, and its own. Both must pass on its code, which is the base's code (with L22, each set runs twice). The panel judges the rest: whether the new tests state what the issue asks (D21's judged question). Once merged, they are the base for every later fix.
  - A new test for a bug goes with its fix, outside the protected paths, as the acceptance test does today. Moving it under them later is a tests-only fix.
  - A fix that mixes code and protected tests has its test changes ignored; the solver submits them as a tests-only fix.
- **D21 and D24:** a dispute's or an appeal's test runs on the run tree with that test added on top. Where the repository declares protected paths, "touches nothing but test files" (D21's machine) means "only paths under `protected`". These are #132's tasks 10.5 and 11.5.
- **Limits, named:**
  - the fix's code runs in the tests' process, so it can still cheat them from outside the protected paths (a special case, a `unittest` patched at import). That stays the judge's and D21's to catch; protected paths stop the plain edit only;
  - a protected test that starts failing on its own (a date, the clock) blocks every fix, as a failing test at the head does today;
  - the paths are the repository's choice: a repository that declares none gets today's behaviour.
- **proof-of-fix's own file:** the repository has no `.pof/check.json` today, so the sandbox runs only `python -m unittest -q` at its root. The genesis head (task 7.1) carries one with its suite (`python -m unittest discover -s tests`, standard library only) and `tests/` protected.
- **Before Sepolia:** required, under the release-candidate gate (L18 item 1, task 7.0).

### L21. The attestation covers every image the node runs (tracked by the owner on 2026-11-19; the route proposed)
- **The gap:** SEV-SNP's report measures what was launched: the firmware and, with a measured boot, the kernel and its command line. The node's image and the test image are pulled after boot (`validator-kit/terraform/node-user-data.sh.tftpl` pulls the node image; `DockerApi.ensure_image` pulls the test image the first time it's needed). Those pulls aren't measured. An operator could run another node image, or a test image that reports every run as passed, under a valid attestation.
- **The rule:**
  1. **One measured, read-only disk.** The checker image is a disk image: a root filesystem under dm-verity, its root hash on the kernel command line that the boot measures. On it: the Docker engine (with containerd and runc), the node image and the allow-listed test image(s) as image archives, and `images.json`, the list of their digests. Writable state (Docker's store, the fixes' checkouts) is on a scratch disk wiped at each boot. At boot the images are loaded from the measured disk into the empty store; nothing is pulled.
  2. **The node refuses any container whose image isn't listed.** In attested mode, `DockerApi` never pulls, and refuses to create a container whose image id isn't in `images.json`. A refusal is a setup error: the node stops, as it does today on a daemon that can't enforce the limits.
  3. **The chain's digest stands for the list.** `Validators`' accepted image digest (`Attestation.image`, the ADR's `AddImage`) is the measurement of this disk and its boot chain, not a Docker image's digest. So Article 3's "one official checker image" is one measured image per version, holding one node image and the listed test images. ### L22. Each validator runs the tests twice (tracked by the owner on 2026-11-19; proposed)
- **The gap:** each validator runs the tests once. A flaky test (timing, ordering, randomness) can pass on one validator and fail on another, splitting the panel, and the split looks like a re-run that contradicts a receipt (D4's challenge).
- **The rule:** the node runs the commands twice on the same run tree (L20), each in a fresh container, one after the other. The tests pass only if both runs exit 0. Both always run. The receipt's `tests` carries both runs (`runs`: each one's exit code, results hash and logs hash) and `flaky: true` when they disagree; the judge's test-run line says so too.
- **The same as D21:** a disputed test already runs twice each way. This brings the ordinary check in line.
- **What it does, and what it doesn't:**
  - a fix that passes only sometimes (a race it brought in) fails more often;
  - a validator's own receipt shows the flakiness, so a mismatch between validators reads as a flaky test, not a false receipt;
  - it doesn't remove splits. A test that passes 9 runs in 10 leaves a panel of 3 unanimous 73 % of the time with one run each, and 54 % with two; a test that passes half the time, 25 % and 44 %. A flaky protected test is the repository's to fix, with a tests-only fix (L20).
- **The time limit and the taxi fare:** the profile's `timeoutSeconds` stays the limit for the whole check, so each run gets half. FeesV3's worst-case deposit (`milliVcpus × timeoutSeconds`) then stays a true bound, with no contract change. The metered vCPU- and GB-seconds are the two runs' sum, about twice a single run's, and **the solver pays them** (L17's taxi fare). At Fargate's rates (`reports/costs-v1.md`, $0.04048 a vCPU-hour), a 300 vCPU-second run is about $0.003, so the second run adds well under a cent per judge, against $0.02–0.12 for the model (`validator-kit/COSTS.md`). Sepolia's profile sets its timeout for two runs of proof-of-fix's suite, with a margin.
- **Before Sepolia:** cheap and recommended, not a gate.

### L23. Panel caps are deployment settings, loose on Sepolia (owner, 2026-11-20)
- **The gap** ([`reports/challenge-drawability-v1.md`](../../../reports/challenge-drawability-v1.md), "The layout precondition"): the operator, host and TEE-type caps are hard-coded, and the owner runs every launch validator. With one operator account, or one host value (the spec counts a host per cloud, and the kit is AWS only), every panel is k = 1. Then a $125 bounty is never judged, because k = 1's limit is $50, and a k = 1 verdict's challenge is never drawn. With every validator but the genesis one on SEV-SNP, the TEE cap holds k to 3. All three cases were tested.
- **What changes, and where it lives today:**

  | Cap | Today | Where |
  |---|---|---|
  | Operator: one seat per operator account, at every k | hard-coded | `PanelsDraw.fits`, `PanelsDraw.sol:270` |
  | Host: at most (k − 1) / 2 per host, from k = 3 | hard-coded | `PanelsDraw.sol:264, 275` |
  | TEE type: at most (k − 1) / 2 per type, from `teeFrom` (3 with at least `TEE_CAP_K3_TYPES` = 5 accepted types, else 5) | hard-coded | `PanelsDraw.sol:276`; `PanelsBase.sol:152, 202-204`; `Panels.sol` `TEE_CAP_K3_TYPES` |
  | Family: at most (k − 1) / 2 per family while `CAP_MIN_FAMILIES` (3) families are seated | **unchanged** (D20) | `PanelsDraw.sol:275`; `PanelScores.sol:46, 219-221` |

- **The rule:**
  - `Panels`' constructor takes a `PanelRules` struct (shared with L24). It holds `operatorCap`, `hostCap` and `teeCap`, each `Strict` or `Off`. They are fixed at construction, keyless and readable (`panelRules()`), carried in `Env` to the draw, and written to the deployment record and the release-candidate record.
  - `Strict` is today's rule for each cap: one per operator; (k − 1) / 2 per host; (k − 1) / 2 per TEE type from `teeFrom`. `Off` drops that cap from `fits`.
  - **The mainnet defaults are all `Strict`.** The deploy script uses them unless told otherwise.
  - **On Sepolia** the record sets all three to `Off` (`--panel-caps launch`), so the owner's validators fill panels whatever their operator account, host and TEE type.
  - The family cap and its switch stay as D20 built them.
- **The k = 1 hold's count follows the same caps:** `PanelsDraw.challengersReady` (`:320-339`) counts challengers without the caps. Under `Strict` it must count only challengers that could sit together under them, so a hold doesn't end while its challenge can't be drawn. Under `Off` the two already agree.
- **Why a setting and not a code change for the launch:**
  - The code stays one codebase, tested both ways. The release candidate (L18) runs with each setting.
  - The record says which applies, as L4 did for the windows.
  - A setting can't be loosened later: a keyless deployment keeps its caps for life (D15). Strict caps for outside validators mean a new deployment, by migration.
- **A new trust point: "one operator runs every launch validator."** At the launch every verdict is one party's. The caps that would keep any operator, host or chip vendor from holding a majority are off, and stay off for this deployment even after outside validators join. Stated in the README's intended use and the paper, beside D20's family trust point.

### L24. Launch panels of 3, and same-size fresh challenges (owner, 2026-11-20)
- **The gap** (report, sections 1–3):
  - At 7 validators a panel of 7 seats everyone. A challenge or test dispute of it needs 7 fresh validators that don't exist. With three known families it waits forever (tested).
  - D27's second draw re-votes with the same 7, and only with fewer than 3 known families.
  - Audits of those panels can't be drawn either (finding 9).
- **The rule:**
  1. **The largest issue-tier panel is 3 at the launch.** k is the largest odd number up to `kTop` that the count and caps allow. The constitution tier keeps `K_MAX` = 7: ADRs and escalated fixes still need exactly 7, `CONSTITUTION_QUORUM` 5 of them, and `CONSTITUTION_MIN_ELIGIBLE` 21. At the launch these expire unjudged anyway.
  2. **A challenge, and a test dispute (D21, the same path), draws a fresh panel of the challenged verdict's size.** The panel comes from outside the challenged panel, its auditors and its replaced judges, and excludes parties. This replaces D4's larger panel. Its step-down stops at that size (`kTop = kMin = k`).
     - **k = 1 keeps D4's 3:** a lone fresh judge's majority could otherwise take a whole bond for a false receipt. The k = 1 hold (`CHALLENGE_K[1]` = 3 challengers) is unchanged.
  3. **D27's second draw stays the fallback:** while fewer than `CAP_MIN_FAMILIES` families are seated, a challenge that can't draw its fresh panel gets a second draw of the same size, the original judges allowed.
- **A parameter, not a launch constant (recommended and chosen):**
  - `PanelRules.kTop`: an odd number from 1 to `K_MAX`. The mainnet default is 7; the Sepolia record sets 3.
  - `PanelRules.challengeSize`: `Larger` (D4, the mainnet default) or `Same`; the Sepolia record sets `Same`.
  - **Why a parameter:**
    - A launch constant would change mainnet's code or leave a fork to maintain.
    - The parameter is recorded and checked like the windows, and the release candidate runs both settings.
    - When the network grows, a new deployment (D15) can move to 7 without a code change.
  - **Where today's constant is used** (each read becomes `kTop` for issue-tier panels):
    - `PanelsBase.drawCounted` (`PanelsBase.sol:243`);
    - `challengeK` and `drawChallenge`'s `kMin` (`PanelsBase.sol:336-338`; `PanelsVerdict.sol:146-147`);
    - the race's worst-case deposit and a challenge's cover (`RaceV3Base.sol:147, 463`; `RaceV3Annex.sol:211`): `kTop` judges, not 7. That lowers what a solver and a challenger post.
    - `SHADOW_PER_DRAW_SMALL`'s test (`PanelsVerdict.sol:71`) and the constitution tier keep `K_MAX`.
- **The k table and the windows, checked with bounty size:**
  - **Limits:** a panel of 3 judges up to $250 at level A and $125 at level B (`PanelsDraw.limitOf`, `PanelsDraw.sol:152-159`; ADR 0004). Every launch bounty ($10, $25, $50 and $125, with $250 bonds) is in range at both TEE levels. Level C is refused (L10), so no other row matters, and no bounty waits for a larger panel.
  - **Challenge windows:** the window is the verdict's `CHALLENGE_WINDOW[3, level]`: **24 h at level A and 48 h at level B**, against 6 h and 12 h for a panel of 7 (`Windows.sol`, `WindowsLib.production`). The bounty doesn't change it.
  - **What must change:** nothing in the windows or the limits. The windows are already per (k, level) and in the record (L4). The unbonding delay is unchanged, since it derives from the longest window, level C's 336 h.
  - The challenge panel's own size no longer depends on k's row in `CHALLENGE_K` (except k = 1).
- **What it gives at 7 validators:**
  - 4 validators stay outside every panel, so random audits are drawable (L19's note) and a challenge's fresh 3 exist.
  - Sampling estimate: the fresh panel fails about 0.2 % of the time with 4 left, and about 7 % with 3 left after an audit. A failure falls to D27, or to L25's retry with a fresh seed.
  - At 15 validators, 12 stay outside.
  - Panels are smaller, so each submission costs about half the checks: #253's $30–50 a month covers about twice the submissions, and capacity serves about twice the panels an hour.
- **Trade-offs, named:**
  - **Fewer judges per verdict:** 2 of 3 decide, not 4 of 7, so one wrong or bribed judge more flips a verdict. The windows are 4× longer (24 h and 48 h), so finality and L9's merges wait longer.
  - **Challenges are fresh but equal, not larger:** a challenge corrects by freshness alone. 2 of 3 fresh judges decide the fix and a false receipt's whole-bond slash. D21's tests stay the main correction.
  - **D27 still re-votes:** among one or two families a second draw of 3 may seat the same judges.

### L25. Challenges always end (owner, 2026-11-20)
- **The gap** (report, section 4):
  - A waiting challenge is retried only on a registry change (`PanelsVerdict.sol:136-140`).
  - A drawn challenge panel with a silent seat no one can fill is never released (`PanelsJudge.sol:155` releases only counted and audit panels).
  - `finalize`, `releaseAudits` and `abandon` all refuse while `challengeOpen`.
  - So a verdict with an open challenge can stay open forever: the bounty is neither paid nor refunded, the challenger's stake and cover stay held, and the judges' bonds stay locked.
- **The rule:**
  1. **A deadline:**
     - Each challenge (filed, disputed, or opened by an auditor's mismatch) has `CHALLENGE_DEADLINE`, counted from its opening.
     - Past it, a challenge **with no panel lapses**.
     - A challenge **whose panel is drawn** lapses only if that panel is released (rule 2). A panel that completes is counted as today, even after the deadline.
     - The longest a challenge lasts is therefore the deadline, or its last panel's reveal deadline plus `STUCK_GRACE`, whichever is later.
  2. **A stuck challenge panel is released as L19 releases counted panels:**
     - When its replacements are exhausted, it ends at its reveal deadline plus `STUCK_GRACE`. Its silent seats are slashed as today, and sealed or revealed seats close unslashed.
     - Before the deadline, the challenge goes back to waiting (rule 3) with a fresh seed. After it, the challenge lapses.
  3. **A retry clock:**
     - A waiting challenge is drawn again with a fresh seed block and snapshot once the registry changes **or** at its `retryAt`, `RETRY_DELAY` after it began waiting, as a waiting submission is (`PanelsVerdict.sol:37-41`).
     - The clock covers what isn't a registry change: a validator un-pausing (`setCapacity`), capacity freeing up, a bad sampling seed.
     - A capacity change doesn't bump the registry's `epoch`, and needn't.
  4. **What a lapse does:**
     - **The original verdict stands.** The window resumes where it froze, as after a rejected challenge.
     - The original judges' `challengeClosed` is called, so they can unbond.
     - Nobody is slashed for the lapse itself.
- **The stake on a lapse comes back (recommended and chosen):**
  - A lapse means the network failed to draw or complete the panel, not that the challenger was wrong. The challenger's stake and cover (a D21 dispute's stake too) return whole, and there's no D21 reward.
  - Seats of a released challenge panel that revealed with receipts are paid as an upheld challenge's panel is: from the check's deposit and the pool, not from the cover.
  - The alternative, the stake to the accused judges as for a rejected challenge, would make the challenger pay for the network's failure.
  - **Against free delay (decided (owner, 2026-11-20)):** a verdict accepts at most `MAX_REDRAWS` lapsed challenges. After that, new challenges of it are refused and it finalizes at its window. Each lapse holds the window frozen at most about `CHALLENGE_DEADLINE`, at no cost to the challenger.
- **`CHALLENGE_DEADLINE` (decided (owner, 2026-11-20)): a new `Windows` field, `challengeDeadline`.**
  - **Production: 120 h.**
  - **The order check:** at least `maxRedraws × retryDelay + seal + reveal + stuckGrace`, which is 99 h in production. So a challenge gets its three scheduled retries and one full round with its grace before it can lapse.
  - Below 2^32 s like the others; minutes in `inMinutes()`.
  - It doesn't change `UNBONDING_DELAY`: a judge named by an open challenge can't withdraw until it closes anyway (`Validators.sol:420`).
- **The invariant:** L19's is restated above to include challenges. #256 and the Foundry invariant test check it with challenges, disputes, silences, pauses and joins applied in any order.
- **Trade-off:** on a network that can't draw a challenge panel, a challenge or D21 dispute ends without correcting anything. The verdict stands, and a wrong pass is paid. L24 makes that rare at 7 validators; L25 makes it finite.
- **Note (2026-11-21, contract batch 5, #290): two gaps around the k = 1 hold, fixed before the Sepolia deploy.** Both came out of #256's integration flake (task 3.27). The contracts are keyless, so both had to be in the deployed bytecode.
  1. **`startWindow` while a challenge is open.** A challenge can be opened on a held verdict (filed, or an auditor's mismatch), and `frozenLeft` is set only when a challenge opens in the window. `startWindow` (anyone) started the window anyway, unfrozen. When the challenge lapsed or resolved, the window resumed with 0 left, and the verdict could be final at once. **Fixed by refusing `startWindow` while a challenge is open** (`NotReady`); the window starts whole once it closes. This is the smaller and safer of the two options: one condition, and no state where a window runs beside an open challenge without a frozen rest. The other option (setting `frozenLeft` in `_startWindow`) would allow that state. Every other path that sets `finalAt` or `frozenLeft` was checked and has no such gap: the count starts a window with no challenge open; `openChallenge` freezes only a window; a resolution and a lapse (from `lapseChallenge` or a released challenge panel's `release` past the deadline) resume only a window; a dispute is a challenge; an appeal is a new submission. Since status can't move from held to window while a challenge is open, `frozenLeft` is always the one set when that challenge opened.
  2. **The k = 1 hold counted challengers its own audits would take.** The hold ended once 3 validators outside the panel and its drawn auditors were ready. Its 2 audits (`K1_AUDITS`, plus a random one 1 time in 10) were then drawn from those same validators, and each auditor sits out of the challenge. So honest audits that caught a wrong lone pass could leave nobody to judge it: the challenge lapsed, and the pass was paid. **Fixed by counting the audits still due in the hold** (`PanelsVerdict._challengersReady`): CHALLENGE_K[1] + `auditsDue` − `auditsDrawn`, plus 1 while the random audit is undecided. That is 6 at the count and 3 once every audit is drawn. Under `Strict` caps the count is of validators that pairwise fit a panel of 3, so any 3 left once the auditors are drawn from them could sit together. This implements D4's hold ("runs only while at least CHALLENGE_K[1] validators are eligible for its challenge panel") and L23's requirement ("SHALL end only when a challenge panel of 3 could be drawn") for the audits, as batch 4 did for the caps. No parameter changes: CHALLENGE_K[1], K1_AUDITS and who sits are as before. The other candidate, drawing a k = 1 verdict's audits before its window starts, gives the same drawability but holds every k = 1 verdict at its count. That would change its shadows' scoring (`heldAtCount`) and leave stuck audits of a held verdict with no release (L19's `releaseAudits` runs only in the window). **What it changes, for the owner to confirm:** #132's judge-panels scenario "The network already has challengers" ("three or more other validators eligible → its window starts at once") now needs 6 ready at the count. With 3–5 the verdict stays held, unpaid, until its audits are drawn and 3 are left. On Sepolia, k = 1 happens only when a panel of 3 can't fill and the bounty is within k = 1's limit ($50 at level A, $25 at B): a $10–$50 bounty during an outage, or while fewer than 3 validators can be drawn. L16's "with 7 the k = 1 hold ends" still holds, since 6 others are ready at 7.
  - **Drawability, tested** (`DrawabilityCasesV3Test.test_n{7,15}_launch_loneWrongPassAudited`, launch rules, $250 bonds; 12 cases per row: $10, $25, $50 × 4 seeds). An outage leaves only the genesis validator drawable, so the verdict is a lone wrong pass. By its count, `m` others are back, and the network stays so. The keeper runs it as the node does, with a watcher re-filing in the window once the audits are in.

    | n | m back | Before batch 5: wrong pass paid | After: paid | After: how it ended |
    |---|---|---|---|---|
    | 7 | 3 | 12 of 12 | 0 | held, unpaid, until the rest came back; then reversed (12) |
    | 7 | 4 | 11 of 12 | 0 | held, then reversed (12) |
    | 7 | 5 | 1 of 12 (a random third audit) | 0 | reversed while held (11); held, then reversed (1) |
    | 7 | 6 | 0 | 0 | window at once, reversed (12) |
    | 15 | 3 | 10 of 12 (2 refunded: an audit stuck) | 0 | held, then reversed (12) |
    | 15 | 4 | 10 of 12 (1 refunded) | 0 | held, then reversed (12) |
    | 15 | 5 | 1 of 12 | 0 | reversed while held (11); held, then reversed (1) |
    | 15 | 6 | 0 | 0 | window at once, reversed (12) |
    | 15 | 14 | 0 | 0 | window at once, reversed (12) |

  - **What's left:** while the network stays short, an audit's challenge on a held verdict can still lapse, and it counts toward MAX_REDRAWS. The verdict then stays held and unpaid. Once 3 challengers are left after its audits, its window starts whole, and a watcher's challenge can be drawn in it. The node's keeper keeps its guard (no `startWindow` while a challenge is open). It now only saves a reverting call.

## Risks / Trade-offs
- **[One operator runs every launch validator]** → decided 2026-11-20 (L23): the operator, host and TEE-type caps are `Off` on Sepolia, so every verdict at the launch is the owner's, and they stay off for this deployment's life (D15). A named trust point in the README and the paper.
- **[Panels of 3 at the launch]** → decided 2026-11-20 (L24): 2 of 3 judges decide, the windows are 24 h (A) and 48 h (B), and challenges are fresh but no larger. Accepted for drawable challenges and audits at 7 validators.
- **[A challenge that lapses corrects nothing]** → decided 2026-11-20 (L25): past `CHALLENGE_DEADLINE` with no panel, the verdict stands and the stake returns. Rare once challenges are drawable (L24); bounded by `MAX_REDRAWS` lapses a verdict (decided (owner, 2026-11-20): the cap of `MAX_REDRAWS`, 3).
- **[A random audit nobody can take refunds a passed fix]** → decided 2026-11-20 (L19): kept as a launch limit. About one passed fix in ten at k ≥ 3 while every eligible validator sits on the panel (7 launch validators); fewer as the network grows past the largest panel. Stated in the README and the paper. Practically moot at the launch once L24's panels of 3 leave 4 of 7 validators free.
- **[The checks bind only this deployment]** → stated in the record, the README and the paper. Nothing else is possible with open code.
- **[One party fakes three active solvers]** → bounded by D29's cap per identity and by disputes; measured by task 3.2. If the sybil of three gains, the owner chooses between a higher minimum, a longer window or a deposit while the repository is small (report v5's untested conditional deposit). **Measured: it gains with one honest solver** (up to +$3,680 a year), and only a deposit closes it. **The owner kept no deposit (2026-11-19): a named trust point** in the README and the paper (L6).
- **[D21's and D24's assumed rates]** → the paid runs that would measure them (#132 tasks 10.3 and 11.3) are not decided; the launch's safety on disputes and appeals rests on assumed rates, a named trust point (ADR 0007).
- **[The head waits for finality, so fixes queue]** → measured by `scripts/time-to-heal.sh`; fixes to different code don't conflict.
- **[Under (a), many offline validators stop `main`]** → readers follow `Heads.head` regardless (`verify-head`); the chain doesn't wait for Radicle.
- **[The owner's node is the genesis delegate]** → named in the record; under (a) it hands over at the first seats; under (b) it doesn't matter.
- **[Validators pay real model costs on play-money fees]** → #253's capacity and budget stop; the owner sets a monthly cap for their own validators.
- **[Test coins make the economics untestable]** → the testnet tests the flow, not the incentives; the paper says so (7.6).
- **[Local chain ids accepted by the constructor (L2 option 1)]** → the deploy script refuses them for any non-local endpoint.
- **[The contracts aren't audited]** (open problems 7.5) → known findings (`drawAudits` repeat calls, the receipt without a seat) are fixed before the deploy (task 3.10); an audit is not in scope, and the README says so.
- **[A fix weakens the tests that judge it]** → the base's protected paths are overlaid on the fix's tree (L20); what the fix's code does from outside them stays the judge's and D21's.
- **[A validator runs an image nobody attested]** → one measured disk, and the node refuses unlisted images (L21). Prompt injection through the diff or the output stays D20's trust point.
- **[Flaky tests split panels]** → two runs, both must pass, both in the receipt (L22). It doesn't remove splits; it shows them as flakiness, and the second run's vCPU-seconds are the solver's.
- **[No lawyer's review]** → the owner decided against one on 2026-11-18 ("no legal check"); the intended-use section and the wording check remain.
